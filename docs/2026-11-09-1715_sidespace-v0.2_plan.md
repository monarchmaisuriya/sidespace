## Context and problem

v1 shipped with three open items: the bookmarks view was untested past its permission prompt, real-site and sign-in behaviour was unverified, and two limits were documented (`window.open` popups open browser tabs; cross-site POSTs to framing-protected sites fail). Research: `docs/2026-11-09-1710_open-items-v0.2_research.md`.

## Goals / Non-goals

Goals:

- Bookmarks view covered end to end (folders, breadcrumbs, search, open, bookmark this page, non-web bookmarks disabled).
- Evidence that panel frames use the normal sign-in (cookies and storage), as a regular test.
- An opt-in live-site suite (`npm run test:live`).
- No false "Page not showing?" hints.
- `window.open(url, ..., 'noopener')` during user activation opens a panel tab (with "Links that open a new window" set to panel).
- Release v0.2.0: version bump, `CHANGELOG.md`, git tag, GitHub release with a zip of the extension.

Non-goals:

- Replaying cross-site POSTs (rejected in research: breaks `Origin`, relays passwords).
- Google sign-in inside the panel (Google blocks it); documented instead.

## Options considered

| Option | How it works | Tradeoffs | Fails when | Completeness |
| --- | --- | --- | --- | --- |
| A. Hint by ping | After each `load`, the panel posts a ping; a live content script answers with its hello | Reflects current state | Content script blocked (then the hint is right to show) | 9/10 |
| B. Keep counting, debounce | Wait longer before deciding | Smaller change | Any extra `load` still misfires | 4/10 |

RECOMMENDATION: A because it removes the dependence on event counts instead of tuning around it.

| Option | How it works | Tradeoffs | Fails when | Completeness |
| --- | --- | --- | --- | --- |
| C. Hook only `noopener` `window.open` | Main-world wrapper asks the bridge synchronously; bridge accepts only with real user activation; returns `null` as the spec does | Page sees no difference | Pages that open without `noopener` keep native popups (on purpose: sign-in popups) | 8/10 |
| D. Hook every `window.open` | Same, for all calls | Covers more links | Breaks sign-in popups that need `window.opener` | 3/10 |

RECOMMENDATION: C because it is the only case where the page cannot tell the difference.

## Design

```
page (main world)                    bridge (isolated world)           panel
window.open(url, t, 'noopener')
  -> dispatch 'sidespace:window-open' (cancelable, sync)
                                     isTrusted? no - event from page script
                                     checks: openLinksInPanel,
                                     navigator.userActivation.isActive,
                                     http(s) URL
                                     preventDefault() + runtime message --> open panel tab
  <- dispatch returned false: return null
     otherwise: call the real window.open
```

- The main-world script installs the wrapper only in frames whose parent is the top frame and whose ancestor origin is a `chrome-extension://` origin; it cannot know our id, so the bridge decides.
- Hint: `checkLoaded` posts `sidespace:ping`; the bridge answers with its hello; the panel treats a hello carrying the already linked token as "alive" without resetting history mode.
- Bookmarks test: harness option copies the extension to a temp folder with `bookmarks` moved to required permissions.

## Risks and mitigations

| Risk | Likelihood | Impact | Mitigation | Noticed by |
| --- | --- | --- | --- | --- |
| Page fakes the window-open event to open panel tabs | medium | a tab opens during a real click | Requires real user activation, http(s) only, visible tab only (panel rule) | e2e: synthetic call without activation does nothing |
| Wrapper breaks pages relying on `window.open` identity | low | site glitch | Only in panel frames; non-`noopener` calls go to the real function | e2e: popup without noopener still opens a window |
| Re-hello resets history mode | medium | wrong back/forward | Same-token hello only marks alive | e2e: back/forward suite |
| Live suite flaky | high | noisy CI | Opt-in only; asserts frame loads, not sign-in | n/a |

## Acceptance criteria

- Given bookmark access, when the user opens the view, then root folders show; clicking a folder shows its items and breadcrumbs; search finds by title; clicking a bookmark opens a panel tab; the star bookmarks the current page; a `javascript:` bookmark is disabled.
- Given cookies and storage set in a normal tab, when the site loads in the panel, then it receives them.
- Given a page loads normally, when 1.5 s pass, then no hint shows, even if the frame fires an extra `load` event.
- Given "Links that open a new window" = panel, when a user click runs `window.open(url, '_blank', 'noopener')`, then a panel tab opens and no browser window.
- Given the same call without user activation, then nothing opens in the panel.
- Given `window.open(url)` without `noopener`, then the real popup opens (sign-in flows keep working).
