## Research: what closes each open item from v1?

- **Bottom line:** Bookmarks can be tested end to end with a test copy of the extension that declares `bookmarks` as a required permission. Sign-in sharing is now verified locally, and live sites load (one false "Page not showing?" hint seen, traced to a fragile design). `window.open` can be handled for the safe case (`noopener`) with a main-world hook. Cross-site POST replay should not be built. Confidence: high for the first three (run in Chromium), medium for live sites (headless Chromium is treated as a bot by Cloudflare).
- **Where we are:** feeds the v0.2.0 plan. About 25 minutes, including four browser experiments.

### What I found

**Bookmarks permission in tests**

- No documented way exists to auto-accept Chrome's permission prompt from Playwright or Puppeteer. `permissions.request()` needs a user gesture, and the prompt is browser UI. [verified: primary, [permissions API](https://developer.chrome.com/docs/extensions/reference/api/permissions)] [verified: tertiary, [chromium-extensions thread on userScripts](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1oLDbmweQ40)]
- A required permission needs no prompt. A test copy of the extension whose manifest moves `bookmarks` from `optional_permissions` to `permissions` runs the same view code with access granted. [inferred: from the docs above; checked in the build]

**Sign-in and cookies in panel frames**

- Experiment: set `SameSite=Lax`, `SameSite=Strict` and `SameSite=None; Secure` cookies plus a `localStorage` value in a normal tab, then load the same site in the panel. All three cookies were sent, and the storage value was visible. [verified: e2e probe, Chrome for Testing 155, output `lax_session=1; strict_session=1; none_session=1 | storage: yes`]
- So a site you are signed in to in a normal tab is signed in inside the panel. [inferred: from the line above]
- Google blocks its sign-in page inside embedded frames, as part of its stance against sign-in from embedded browsers. [verified: primary, [Google developers blog](https://developers.googleblog.com/guidance-to-developers-affected-by-our-effort-to-block-less-secure-browsers-and-applications/)] [verified: e2e probe, `accounts.google.com` in the panel shows "Error 401 (Bad Request)"]

**Live sites (headless Chrome for Testing 155)**

- The false hint came from the hint heuristic: it counts frame `load` events against content-script hellos. Any extra `load` event without a new document (cause unverified; three timed reruns did not reproduce it) produces a hint. Asking the frame whether a live page is there, after each load, does not depend on counting. [verified: e2e timeline probe shows each normal load is one hello then one `load`] [unverified: what produced the extra `load` event; check would be a timeline capture of the failing run]

**`window.open` popups**

- Content scripts can run in the page's own JavaScript world (`"world": "MAIN"`); the docs warn the page can interfere with such scripts. [verified: primary, [content scripts manifest](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts)]
- Sign-in popups ("Sign in with Google" and similar) rely on `window.opener`. Turning them into panel tabs would break the sign-in. [verified: tertiary, [HubSpot forum on OAuth popups](https://integrate.hubspot.com/t/why-oauth-sign-in-pages-google-sign-in-button-has-to-open-on-a-new-page/8990)]
- A page that calls `window.open(url, target, 'noopener')` (or `noreferrer`) declares it needs no link to the new window, and the spec makes such calls return `null`. Turning exactly those calls into panel tabs changes nothing the page can observe. [inferred: from the HTML spec rule that `noopener` returns null]

**Cross-site form POSTs**

- The only way to unlock them would be to cancel the submission and resubmit the form from the panel page. That changes the `Origin` header to `chrome-extension://...`, which breaks CSRF checks. It would also pass form fields, often passwords, through extension messaging, and file inputs cannot be relayed. [inferred: from how form submission sets `Origin`, and what runtime messages can carry]
- Recommendation: keep it as a documented limit; the "Open in a browser tab" hint already covers it.

- New `src/content/window-open.js` (main world) + bridge handling, only in panel frames.
- New opt-in live-site suite; README sign-in guidance.
